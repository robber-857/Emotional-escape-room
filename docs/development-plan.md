# 开发计划、验收与交接

日期：2026-09-25。当前仅完成需求分析与规划，应用尚未初始化。

## 1. 首版范围

用户最终确认：
- 完整 L1 → L2 → L3 → L4 → 16 型结果。
- L2 四组全部制作、每局全部提供；不随机抽组。该决定替代本次沟通早先的“每局三组”。
- 事件分值和关卡权重可修改，初始 2:3:3:2。
- 支持桌面和手机横屏，手机竖屏弹窗原文“为了保证用户体验请翻转手机为横屏”。
- React + Next.js 前端、FastAPI 后端。
- Eltondev 开发，PR 合并 MVP_branch；George 部署。

本次 MVP 不在本游戏项目中实现登录或注册操作。最终数据需汇总至 ZENEWE 平台数据库；登录、注册及相关数据同步不属于本项目的开发目标，由 George 在最终部署后负责迁移与整合。

用户新增确认纳入 MVP：断网、关闭页面、主动退出后的场景保存与恢复，详见 [专项设计](save-and-resume.md)。

建议纳入 MVP：匿名会话、继续游戏、关键行为持久化、规则版本、结果快照、基础可访问操作、音频开关、错误恢复、自动化测试与部署交接材料。
本项目后续可另行评估的范围：跨设备存档找回、真人匹配、支付、社交分享卡、完整可视化评分后台、运营分析面板、完整离线模式。登录、注册和 ZENEWE 账号数据同步由 George 的平台迁移工作负责，不列为本游戏开发任务。结果页不出现无功能的真人匹配按钮。

## 2. 开发顺序与工作量

以下为单名全栈开发者的工作量估算，非承诺交付日期。假设设计素材可导出且可用、产品反馈及时、没有账号和真人匹配需求。加入持久化草稿、outbox 与中断恢复验收后，总计约 29–42 个工作日（约 6–9 周）；内容等待、额外美术、重大改稿和 George 的部署排期另算。各阶段包含其测试，不另加重复的测试周期。

| 阶段 | 工作量 | 交付与退出标准 |
| --- | --- | --- |
| P0 需求与交互冻结 | 2–3 天 | 逐项事件/分镜清单、四组 L2 路线、缺失素材、评分边界、结果文案清单；阻塞规则有结论 |
| P1 项目骨架与游戏壳 | 4–6 天 | Next.js/FastAPI/DB/迁移、会话 API、健康检查、Grid/Flex + SVG 原型、竖屏提示、检查点/草稿/outbox 与继续入口、基础 CI |
| P2 评分与行为闭环 | 3–4 天 | 规则 schema、幂等事件、状态版本、归一与权重、16 型映射、旧会话规则锁定、逐 action 计分 trace、独立关卡评分快照、四关加权对账；纯函数和集成测试通过 |
| P3 L1 完整纵向切片 | 3–4 天 | 河边到对岸及人物/灯全路径；真实 API 存档；桌面和手机横屏可玩、刷新可恢复 |
| P4 L2 四组 | 6–9 天 | 座位钥匙、半开门、耳环计时、按 Figma 实现家具布局与对应 action；拒绝路线待设计师冻结；四组全提供 |
| P5 L3 + L4 | 4–6 天 | 风暴与三类环境控制、携带一件物品、四个出口、过场和退出路径闭合 |
| P6 结果与全链联调 | 4–5 天 | 结果快照、16 型内容、重玩、浏览器返回、多标签冲突、响应丢失、强杀恢复、离线退出补同步、资源优化 |
| P7 验收与部署交接 | 3–5 天 | 回归证据、环境变量、启动和迁移文档、素材清单、George 测试环境问题闭环 |

执行原则：先把 L1 从前端动作一直打通到后端存档与评分，再复制成熟结构开发其余三关；不先堆完所有静态页再补行为模型。P2 可以用合成动作验证四轴和结果，不假装已完成四关 UI。

主要工作量风险是最终 Figma 素材拆分、交互到 action 的映射、各分支补画面以及 16 型素材到位时间；家具不另做自由布局自动分类算法，结果解释与插画等待用户后续提供 Figma。若时间缩短，优先降低装饰动画复杂度，不削减用户已确认的 L2 四组，也不改成纯选择问卷。

## 4. 小功能 PR 与持续 review

执行细则见 [PR 代码审查与 UAT 业务验收规则](pr-review-and-uat.md)。下面是工作主题而不是单个 PR 的固定大小：每个主题按独立可验证功能继续拆分，L2 按四组交互拆分，L3、L4 与结果分别提交。

所有开发提交位于 Eltondev，目标分支明确指定 MVP_branch。一个可独立验证的小功能完成后发 PR；不直接推送 MVP_branch，不绕过评审。

| PR 建议主题 | 内容 |
| --- | --- |
| docs: architecture and implementation plan | 本次设计文档，规则标为草案 |
| chore: application foundation | 单仓库骨架、会话、迁移、CI、方向提示 |
| feat: versioned scoring and action pipeline | 行为契约、规则版本、评分测试 |
| feat: complete L1 journey | 首个完整可玩关卡 |
| feat: L2 interactions（多个 PR） | 座位/钥匙、半开门、耳环、家具分别交付 |
| feat: L3 / L4 / results（分别提交） | 风暴控制、携带物品、出口与结果各自验证 |
| test: acceptance and deployment handoff | 验收修复、交接文档 |

顺序 PR：前一个合并后，同步 origin/MVP_branch 至 Eltondev，再开始后一个，避免同一分支的 PR 被后续未完成工作扩大。合并策略由仓库维护者决定；若使用 squash，需同步分支历史，不强推抹掉 George 的工作。

未来已获发布授权时，示例命令：
~~~
git push -u origin Eltondev
gh pr create --base MVP_branch --head Eltondev --title "<明确的变更目的>" --body-file "<本地描述文件>"
~~~

当前规划交付不自动提交、推送或合并，也不代表分支保护已启用。建议维护者给 MVP_branch 配置 PR 必需、必过检查、禁止 force push；George 作为评审/部署协作者的权限需仓库管理员确认。本次未检查邀请接受状态。

## 5. 验收矩阵

George 按实际构建 commit 与内容/评分版本执行阶段 UAT；最终 UAT 包含四关串联、真实后端追踪面板与存档恢复。PR review、自动化测试、实际业务验收分别记录，未执行不得标记通过。追踪面板与验收准备的新增工作量在 P0 拆分后重新估算，前述 29–42 天是加入该要求前的估算，不将新增交付默认为零工时。

| 层次 | 核验内容 | 证据 |
| --- | --- | --- |
| 评分单元测试 | 向量、互斥、顺序、边界、权重、16 型、旧版本 | 固定输入输出与路径测试报告 |
| 状态机测试 | 所有合法路线可达终态，拒绝不死锁，不能跳关 | 路径/转移覆盖报告 |
| API/数据库 | 幂等、回滚、越权、revision 冲突、刷新恢复、finalize 只能一次 | 使用独立测试库的集成报告 |
| 组件交互 | 触屏替代 hover、键盘、弹窗焦点、拖放、音频禁用 | 组件测试及必要手测 |
| 浏览器 E2E | 开始→四关→结果→重玩，断线/刷新/重复提交 | Playwright trace 与失败截图 |
| 视觉/设备 | 背景命中一致、手机横屏、safe area、字体可读 | 指定尺寸截图 + 真机记录 |
| 评分内容回归 | PDF 逐行复核、冲突决议、规则 hash | 源行为清单与已发布版本 |
| 环境验收 | George 环境上的静态资源、API、会话、存档与完整结果 | 完整实际游玩记录，不只 /health |

初始视口验收：桌面 1366×768、1440×900、1920×1080；手机横屏 667×375、844×390、932×430；竖屏 375×667、390×844。尺寸只是覆盖样本，还要验证宽高连续变化和浏览器工具栏引起的高度改变。至少覆盖桌面 Chromium、iPhone Safari、Android Chrome；触控真机与浏览器模拟应分别记录。

关卡验收重点：
- L1 四种过河路径均能完成；船桨前 4 次仅进度，第 5 次计分一次，恢复和重试不重复；人物优先、灯优先、灯未亮带走、不交谈等分支成立。
- L2 四组均出现；钥匙首次失败符合剧情；拒绝钥匙/半开门后的路径等待设计师决定；耳环持续寻找 >15 秒触发长寻找，返回时 <=15 秒按短寻找，竖屏/后台不计时；家具按最终 Figma 交互触发对应 action。
- L3 各已明确 action 可独立测试；不开/不关门时风暴触发与结束等待设计师讨论，相关流程验收标为 Blocked，不擅自补剧情。
- L3 只能携带一个已确认物件，“携带是”与物品分值累加，各阶段只计一次；确认前切换不额外计分，九种物品和“不带”均覆盖。
- L4 四出口只有一个最终确认值，提交失败仍留在可恢复状态，不能重复结算。
- 结果不展示未完成会话的假类型；重玩不覆盖旧结果。
- 每关建立独立用例，逐 action 核对规则、四轴净变化与关卡累计；本关结束立即可查原始/归一总分，最后核对四关快照的 20/30/30/20 加权结果。未完成整局也能验收单关。
- 场景恢复覆盖正常关闭、强杀、断网退出、家具草稿、响应丢失与重复补发；见专项设计的 11 项验收。

## 6. George 交接内容

开发方准备：
- 前端/后端独立 build、start、test 命令与锁文件。
- .env.example：数据库连接、允许来源、会话签名/凭据密钥、外部 URL、资源路径、日志级别等说明；示例不放真实密码。发布规则版本保存在数据库 release 指针中，避免多份环境变量产生冲突。
- 数据库迁移、首次载入内容/规则步骤、可逆迁移限制、备份与回滚顺序。
- 版本固定的资源 manifest、字体/音效/图片来源和加载检查。
- /health/live 与 /health/ready、结构化日志与 request_id、异常排查说明。
- 构建产物或容器定义（具体方式与 George 对齐），CI 状态与已知限制。

George 负责：
- 环境与域名、HTTPS、反向代理、数据库和备份、运行时秘密、静态资源托管、发布和回滚执行。
- 在测试环境运行迁移并验证规则版本、会话 Cookie 与 API 路由。
- 向开发方提供可用测试入口与日志访问方式，用于验收问题定位。
- 最终部署后负责登录、注册及相关数据同步的迁移与整合，将游戏数据汇总至 ZENEWE 平台数据库；平台字段映射、身份关联与迁移校验由 George 确定。

共同验收：
- 新环境从空数据库完成迁移、配置发布、玩完四关并读取结果。
- 新版上线时在途会话能继续旧版本，资源旧版本仍可读。
- 关闭浏览器后持久 Cookie 仍识别本人；重开恢复场景，草稿与评分不重复；数据库备份包含检查点与草稿。
- 回滚应用/规则后，旧结果仍能读取，数据库 schema 保持兼容。
