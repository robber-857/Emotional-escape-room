2026-09-28。范围：L2 API/状态机/家具几何、L1 会话门槛、事务和幂等、计时上界、客户端待同步请求及服务器记录页。基于 Eltondev 当前工作区，保留此前未提交修改；未修改正式分值。

## 已发现并修复

| 问题 | 影响 | 修复与验证 |
| --- | --- | --- |
| 每次 search-time 可独立使用 250ms 容差 | 高频请求能累计超出真实经过时间的活动报告 | 同时校验本次增量与本寻找段的累计服务器经过时间，容差不能逐请求累加；新增精确边界测试 |
| 记录页只使用快照内的已接受动作，从当前状态解释历史 | 无法查看拒绝；历史结果容易与后续状态混淆 | 直接 GET `/events`，每条显示数据库来源、服务器判定、ID、接收时间、前后版本、规则、固定事件结果与证据；新增逐条 API 对账测试 |
| 无变化/无效家具落点被客户端当作同步故障 | 正常操作可能要求无意义的重试 | 保留服务器拒绝回执，UI 提示原因并继续；服务器模式的落点交由后端校验；新增无变化流程测试 |
| 迟到响应无条件清除同会话 pending | 可能删除另一标签页的新待提交请求 | 只在本机 pending ID 与响应请求 ID 相同才清除；新增迟到响应测试。服务端行锁与版本仍为最终并发保障 |
| 未初始化 L2 的 events 返回空列表 | 混淆“未开始”与“已开始但没有事件” | 返回 404 L2_NOT_STARTED，与读取快照一致 |

## 权威记录契约

新增回执保存 `previous_version`、`validation_version=l2-validation-v2`、`authority` 与 `outcome`。`authority` 区分输入 `client_claim`、判定 `server`、记录 `server_database`；不会宣称输入本身不是来自客户端。`outcome` 在接受动作的同一事务内固定保存，不从后来状态重建。拒绝回执 outcome=null、版本不变。

旧回执没有 outcome 时不补造历史结论；界面明确显示旧记录缺少逐事件结果。结构不合法的 422、身份校验失败以及 ID 换载荷的冲突仍按接口契约拒绝，不新建业务回执；记录页对此有说明。

## 复查后仍保留的边界

- 寻找活动报告不是服务器独立计时。容差修复能阻止时间上界被反复突破，但不证明后台/离线/真人活动。强退丢失未落盘片段、慢网暂停等仍需后续活动协议与真机测试；不作为已完成的正式计分依据。
- L2 最终通关/拒绝通行、正式评分策略/贡献表/结算尚未确定，保持 pending，不自拟。
- 匿名凭据、单请求 pending 与 PostgreSQL 服务端进度是现有恢复方案，没有账号找回或完整离线队列。
