# 评分事件、可编辑得分表与回执优化开发任务

2026-09-30。状态：**开发方案，尚未实现评分引擎、评分账本或下述回执升级**。本次发布的是已有本地 L2/结果页改动和这份开发任务；现有 API 仍返回 pending_configuration。本文件覆盖旧审计中“合并分值待拆分”的错误理解。

## 1. 已确认规则：操作记录不等于评分项

原始操作 → 服务端验证事实 → 固定评分条件 → 一个评分结果 → 得分表查向量。保持全部原始操作回执，不按回执条数累加。

| 评分项 / 互斥选项 | 成立条件 | 一次向量 |
| --- | --- | --- |
| l1.crossing / bridge | 同旅程修桥成功 **且** 走桥到对岸 | A+1、F+1 |
| l1.crossing / swim | 游泳到对岸 | A−1、F−2 |
| l1.crossing / ring | 使用救生圈到对岸 | A−1、F+1 |
| l1.crossing / boat | 第5次搜草修好船 **且** 第5桨到对岸 | A+1、F=0 |
| l1.lamp / lit_taken | L1-02结束时已点亮且已带走 | F+2 |
| l1.lamp / lit_left | 最终已点亮、未带走 | F=0 |
| l1.lamp / unlit_taken | 最终未点亮、已带走 | F=0 |
| l1.lamp / unlit_left | 最终未点亮、未带走 | F−2 |
| l3.environment / both | 风暴六项回答完成；关窗关电视 | F+2 |
| l3.environment / window | 风暴结束；关窗开电视 | F=0 |
| l3.environment / television | 风暴结束；开窗关电视 | F=0 |
| l3.environment / neither | 风暴结束；开窗开电视 | F−2 |

过河四选一；灯四选一。修桥本身、修船本身、拿绳、拾取木板、前4桨、上船、单独拿灯/点灯不另分配上述向量。修好桥后选择游泳，只命中游泳结果，不命中走桥结果。灯的拿/不拿、亮/不亮操作分别留痕，结算取最终事实；“否后是”以最终状态归类，不累计互斥选项。未点击不能伪造为一条否回执；已完成场景里的最终未拿/未亮，可作为结果事实并标注来源为终态。

**电视组合已确认**：用户指定原表电风扇改为电视，R51–R54数值保持。以服务器六项回答完成、storm转carry的回执作为截止证据，读取choices.window与choices.television，四选一。任一尚为null则等待完整答案，不作false；之前否后改是按截止时终态选择，操作顺序不影响结果。独立window/television动作没有额外F分。规则与分值已确认，但评分引擎/账本仍待实现。

男女交谈是不同事件，各最多一次。机械操作、重复执行不重复得分。只对已配置的“否”结果执行分值；明确 no_effect 的否不改变分数。**不能把全部否统一无分，也不能给全部否补负分。** 长搜索严格 >15000ms 不变。家具只按最终确认结果结算。

## 2. 给开发人员的配置约定

> 评分条件固定后，日常改分只改 `apps/api/app/config/event-scores.json`。改事件、组合条件或结算时点才改规则代码。这个路径是待实现的目标，不是当前已生效的配置入口。

建议拆为两个版本：

- `event_definition_version`：代码维护稳定 group_id / option_id、组合条件、互斥关系、截止点、来源证据；普通改分不动。
- `event_score_version`：上述得分表维护每个固定结果的 A/V/T/F。用户只改向量，发布为新版本，不覆盖已发布版本。

得分表结构示例见 [配置草案](examples/event-scores.v1.draft.json)。只作接口示例，不是完整可启用配置。`vector` 中数字0为已测量中性值、null为明确未测量；`status=unconfigured` 的 vector=null 才是缺分。`no_effect` 不改变分数，也不自动增加测量样本数。四维全null的“不携带”可记为 not_measured。发布校验：固定ID集合、四轴、有限数值、配置状态和定义版本必须合法；未配齐相关项不得输出完整正式结果。

关卡权重继续使用已有 `apps/api/app/config/scoring-weights.json`，默认20/30/30/20，版本独立。新增评分策略发布命令应校验并冻结定义版本、分值版本、权重版本及内容hash；部署后所有API进程使用同一个已发布配置。禁止每个请求从可能正在编辑的文件读取半成品。

建议在旅程创建时固定整套版本与内容hash；旧会话没有绑定版本时标记 legacy_unbound，不偷偷应用最新分值。明确授权的历史重评另建 evaluation_id，关联原旅程和源证据，不覆盖旧评分或把新旧结果相加。最终归一化、人格画像和总分算法仍待用户提供，本任务不编造。

## 3. 回执与账本（五项待开发）

| 任务 | 需要实现 | 主要文件 |

| P1 固定评分事件与原因 | 原始回执增加 state_changed、派生 group_id/option_id、原因与关联评分记录；拒绝不派生加分 | l2_api.py、l2_receipts.py、scoring.py |
| P2 可追溯向量 | 新增不可变评分账本，记录来源动作ID、结果截止版本、定义/分值/权重版本、实际向量快照和hash | db.py、新Alembic迁移、独立评分模块 |
| P3 固定最终家具证据 | 最后确认ID、布局hash、确认版本、固定分类结果、截止点一同冻结 | l2_domain.py、l2_receipts.py、l3_api.py |
| P4 相同布局结果稳定 | 把最终空间分类与“相比上次移动了什么”分开，重复确认相同布局不改变最终评分事实 | l2_layout.py、前端layout.ts及两端测试 |
| P5 如实标注搜索计时 | 保存分段ID、累计报告ms、墙钟上界校验信息、timing_source；timing_verified保持false | l2_api.py、l2_receipts.py |

建议评分回执字段：`evaluation_id, group_id, option_id, status, reason, source_action_ids, cutoff_version, event_definition_version, event_score_version, weight_version, vector, policy_hash, layout_hash, created_at`。回执给出**未加权的本次事件向量**，权重/归一化只在后续结算层处理，避免重复加权。按一次操作可派生0至多个评分结果设计，不强行一回执一分值。

原因至少包含：APPLIED、WAITING_FOR_COMPONENTS、AWAITING_FINALIZATION、ALREADY_SCORED、NO_SCORE_ON_NO、MECHANICAL_STEP、NOT_MEASURED、UNCONFIGURED、REJECTED。status与reason分开：拒绝、缺分、未到条件、未测量不是零向量加分；F=0等真实中性结果也不能被过滤掉。

**事务和去重：** 保留现有 action_id 幂等；另对 `(session_id, evaluation_id, group_id)` 加唯一约束，组内互斥选项只能产生一个最终结果。新action_id重复操作、刷新、并发、重试不能再入一份分。事务内验证事实、写状态、原始回执及评分记录；响应丢失仍用原ID重试。换评分版本不能绕过该约束再次累加，重评必须有新evaluation_id并单独展示。

**不要改旧回执：** 现有 l2_events.result 已保存动作当时 outcome，应继续不可变；后续补分/重评另存账本并引用旧ID。/events 返回旧事实，增加独立 scoring 查询或明确的关联区，不用当前snapshot重造历史。L1缺逐动作outcome时按已接受记录及规则版本重放；缺必要记录应报证据不足，不推测。

## 4. 家具最终结果与跨关截止

当前 classify(layout, baseline, triggered) 的 tidy 依赖本次相对baseline是否移动，baseline每次确认都会更新；同一布局再确认可能由true变false。triggered是历史曾经成功，classification.events是首次触发通知，两者都不能替代最终布局结果。

推荐修复：保存不可变 initial_layout，最终分类只依赖 canonical_layout + 固定参考布局 + 分类版本；把 since_previous_confirm 的变动信息另放 diagnostics。若保留“合理且相对初始布局有有效移动”作为tidy定义，必须明确这是原型定义，不冒充真实整齐度或V6.2四分位。同布局hash重复确认复用同一final classification；回到初始布局、有效布局后变不合理、恢复/撤销均按最后确认重算，不能沿用历史成功。hash包含四件家具排序后的规范化坐标与分类版本，先明确坐标精度，避免浮点显示差异产生假变化。

**推荐截止点（待开发落实）**：首次成功创建L3时，在现有同一个父会话行锁和事务中冻结L2。冻结最后有效确认回执ID、布局hash、证据截止version，并结算一次；之后拒绝L2变更。仅GET L3或已有L3重试不能重新冻结。L2.exitDoorOpen只代表可进入下一关，不代表布局得分或已经冻结。若最后确认之后还有未确认草稿，推荐阻止进入并提示确认/放弃草稿，不能悄悄拿未确认状态评分。

旧旅程已经进入L3却没有冻结记录时，不按当前L2快照补称“当时最终布局”；迁移标明 legacy_unsealed，按可验证历史或人工重评处理。迁移先备份并在独立测试库演练，不删除玩家库。

## 5. 搜索与否分支

当前API已约束累计增量和墙钟容差，保留这些校验。新增 search_segment_id 与结束原因（找到、主动返回、重新开始）便于区分重试与新搜索段。多段如何取最长/最后/合并时长属于评分条件，尚未确认，不擅自相加。计时值只是客户端活动报告，不标成服务器验证了注意力。

>15秒命中长搜索；15秒整不命中。原表短搜索写<15秒，15秒整的短搜索向量未明确，应保留待配置，不默认为0。找到耳环与搜索时长是不同事实，是否另有找到分由得分表决定。显式否、没做、未到场景、未结束分别存来源，场景结束前不推定“放弃”。

## 6. 实施顺序与验收

1. 固定组合规则及尚未决定项，建立完整得分表schema与发布校验。先完成过河/灯/关窗与关电视等已确认组合；家具向量、背包等尚未定义项保留unconfigured，电视不再属于待定项。
2. 修复家具稳定分类、补计时分段事实，再建冻结记录与评分账本迁移。前后端分类版本同步，旧规则版本必须能识别。
3. 接入L3创建时冻结、事务去重、评分回执查询和调试记录页；最后接入用户提供的总评分算法。

验收必须覆盖：仅修桥无分；修桥+走桥恰好一次；修桥后游泳只得游泳分；修船未划完无过河分；五桨只一次；灯四组合准确且仅一条、拿/亮顺序互换相同、否后是无重复分；新ID重复/同ID重试/并发不双计；重复确认同布局结果不变；改成无效布局不沿用旧成功；冻结与并发移动只能串行产生一个确定结果；发布新分值不修改旧旅程结果；缺分、NA、0、否无影响有区别；14999/15000/15001ms及计时分段、伪造超时和容差累计。

单元测试、独立PostgreSQL并发/迁移测试、桌面与模拟触屏的真实回执对账分别记录；不能用SQLite跳过项或页面能开替代数据库证据。

电视专项验收：true/true=F+2，true/false=F0，false/true=F0，false/false=F−2；任何未答null不计；四种操作顺序、否后是、刷新、重复请求、六项完成后的重复动作均不能提前或重复加分；其他三轴为明确NA。
