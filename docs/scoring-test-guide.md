# 服务端计分与手动测试

2026-09-30：评分引擎、数据库账本、逐事件反馈和归一化已实现。画像分类规则仍独立待配置。

## 计算方法

用户确认：每关合成一个总分，再按四关权重汇总，同时保留 A/V/T/F 明细。

1. 服务端确认评分组合成立后，该组只记一次。关卡原始总分 R 为已命中结果中所有数值维度之和；NA 不参与，明确的 0 保留。
2. 固定评分版本下，按每组互斥选项的向量合计求最低值、最高值，再分别跨组相加得到 L、U。可选组计入“不触发 = 0”的可能性。不能把互斥选项全部累加，也不按玩家已触发事件动态改变分母。
3. 关卡分 = 100 × (R − L) / (U − L)。没有测量或 U = L 时不生成数值。进行中或配置不全时，只展示带星号的暂算值。
4. 四关完成且配置齐全后：最终分 = L1 × 20% + L2 × 30% + L3 × 30% + L4 × 20%。缺关不补零、不重新分配权重。四维明细不再单独参与第二次加权。

例如 L1 理论总分范围为 [-9, 4]，游泳 -3、灯未点亮且未带走 -2，合计 -5，归一化约 30.77。L4 海岸结果 +2，对应范围 [-2, 2]，归一化 100。

## 手动测试

- 打开 http://localhost:3000，从第一幕开始**新旅程**，右下角展开“服务端计分”。旧旅程没有评分版本绑定，不自动补分。
- 面板每秒读取服务端账本，显示本次原始总分变化、A/V/T/F、各关分数、事件 ID、结算证据和待配置项。打开提示框等纯前端动作不会产生加分。
- 组合事件在截止点结算：灯在 L1 结束；窗／电视在风暴六项回答完成时；家具在第一次确认摆放时。过程动作显示等待或不单独计分。
- 同 ID 重试返回原始回执；新 ID 重复结算也不重复加分。刷新保留服务器记录。断网时显示读取错误，不把旧数据冒充新反馈。
- 第四关的结果弹窗可点“稍后再看”，再展开计分面板。结果页也显示各关合成分及最终分状态。

## 尚缺的正式定义

- L2 家具三项真实样本池四分位阈值；原始靠墙窗、重合整齐度、调整次数已记录，桌前椅使用缩小的重叠核心，没有朝向或旋转判定。
- L2 座位、重试放弃、探索、搜索的部分条件／截止点及未配置结果。
- L3 背包、未开又关门等未配置结果分值。

这些空缺影响固定理论范围，因此即使本次选到已配置选项，相关关卡仍不能生成正式归一化分及最终加权分。界面暂算值仅用于测试，不是正式结果。

## 配置与验证

`apps/api/app/config/event-scores.json` 管理数值；`scoring-weights.json` 管理关卡权重；`l2-04-quartiles.json` 管理四分位池。条件由服务端规则维护。发布新版本并重启 API 后只绑定新旅程；既有旅程保留完整配置快照与哈希，不被新分值改写。

正式反馈来源为动作回执 `score_effect` 和鉴权接口 `GET /api/v1/sessions/{id}/scoring`。旧 `scoring` 兼容字段不作为新计分依据。动作状态、账本和计分回执在同一事务提交。

本轮验证：PostgreSQL 222 项通过（包含并发、幂等、回滚和迁移）；前端 67 项及类型检查通过；桌面 1440×900、触屏 844×390 浏览器联测通过。浏览器覆盖真实 UI 计分展示、刷新、断网恢复，L2/L3 前置过程部分使用鉴权 API，并非所有事件的人工 UAT。
