# PR 代码审查与 UAT 业务验收规则

日期：2026-09-25。适用于情感密室 MVP 的逐步开发、George 的代码 review 与业务验收。
状态：项目协作规则与实现要求；不表示已配置 GitHub 分支保护、已完成测试面板或已通过验收。

## 1. 两项检查分开记录

| 项目 | 代码审查（PR Review） | 业务验收（UAT） |
| --- | --- | --- |
| 目的 | 判断代码是否正确、清晰、可维护，是否符合已确定的逻辑 | 判断玩家实际体验与后台处理是否符合需求 |
| 对象 | 明确 commit SHA 的 diff、测试、接口与迁移 | 明确构建版本的游戏、真实后端记录和验收用例 |
| 负责人 | George 主审，开发方解释与修正 | George review 业务过程；项目负责人确认体验和规则含义 |
| 通过依据 | 相关检查通过、阻塞意见解决、目标版本获得明确认可 | UI 与后台证据一致，用例实际执行并记录结论 |
| 不可替代 | CI 通过不等于 George 已 review | UI 截图、自动化测试或 /health 正常不等于 UAT 通过 |

可以先合并基础设施等已通过审查的小 PR，再在测试环境分批 UAT。涉及玩家行为的 PR 应附功能演示；最终交付必须同时具备代码审查与完整 UAT 结论。

本 MVP 不开发登录、注册及账号数据同步；ZENEWE 平台数据库整合由 George 在最终部署后负责迁移。本文件要求的存档访问控制与测试追踪权限仍需实现，可使用测试环境访问机制，不要求增加游戏注册/登录页面。

George 的 GitHub 账号、评审权限和测试环境访问凭据应在首次 PR/UAT 前核对，不猜测用户名，不以“已邀请”代替已可访问。

## 2. 责任分工

- 开发方（Elton 与开发协助工具）：按小功能实现；解释逻辑；自测；提交 PR；准备可复现演示、后台追踪与问题修复。不自行宣称 George 已批准。
- George：逐批 review 代码；检查实现与后台行为；反馈问题；负责测试环境与部署。代码 review 结论不自动代表客户已确认新增业务规则。
- 项目负责人：确认需求冲突、评分含义、文案与范围变化；参与 UAT 并记录业务结论。当前未确定具体人员时不假定由 George 代签。
- 合并执行者按仓库权限和团队约定确定；必须满足本文件的合并条件，不能因开发工具拥有管理员权限而跳过审查。

## 3. 分支与逐步交付

固定流程：

开发一个可独立验证的功能 → Eltondev 小提交 → 本地验证 → 推送 Eltondev → PR 指向 MVP_branch → George review → 同一 PR 修正 → 检查与复审 → 合并 → George 部署测试版本 → 记录阶段 UAT。

- 一个 PR 对应一个清晰业务目标或一个独立技术基础能力，不以整个关卡或整个开发阶段作为必须合成一大包的单位。
- 单个目标应包含必要前端、后端、存档和测试；基础能力 PR 可使用明确标为合成的测试，不假装已有完整 UI。
- 提交信息说明具体变化，避免“update”“AI generated code”或把大量无关格式化混入业务修改。
- 实现前先说明本次范围、预计可见效果、后端行为和验收步骤；途中发现评分或剧情歧义先记录决定，不让代码替产品做决定。
- 需要早期反馈时开 Draft PR；准备好 review 后明确状态、未完项和验证结果。Draft 不等于已获合并批准。
- 使用同一个 Eltondev 发 PR 时，同一时间保持一个待合并功能 PR；评审期间该分支只追加当前 PR 的修复，避免推送下一功能扩大 diff。
- 前一个 PR 合并后获取最新远端状态，将 MVP_branch 的更新同步到 Eltondev，核对差异后开始下一批。遇到 squash/rebase 历史差异，先检查祖先关系和实际内容；不盲目重置或 force push。
- 若需要并行功能开发，先调整分支协作方案；不能默默改变用户规定的开发分支。
- 不直接推送 MVP_branch，不把 PR 自动合并当默认操作。推送/PR 通知通过 GitHub 工作流完成，其他渠道联系 George 另行安排。

推荐第一批拆分：

| 顺序 | PR 范围 | George 可以核对的内容 |
| --- | --- | --- |
| 1 | 需求、架构、评分与协作规则文档 | 逻辑边界与尚未冻结的规则 |
| 2 | 应用骨架、健康检查与接口契约 | 前后端启动、职责划分 |
| 3 | 创建会话、检查点与继续入口 | 新建、关闭再开、本人访问限制 |
| 4 | 本地草稿与断网补同步 | 响应丢失、退出恢复、重复请求 |
| 5 | 行为与评分引擎、只读追踪基础 | 规则全匹配累加、同规则去重、计算来源 |
| 6 | L1 修桥过河完整路径 | 点击到状态、存档、评分的全过程 |
| 7 | L1 其他过河路径 | 路径互斥与合法终态 |
| 8 | L1 人物与灯 | 顺序、复合行为和避免重复计分 |

L2 按座位/钥匙、半开门、耳环、家具分别提交，最终验收每局四组全部提供。L3 风暴控制、携带物品、L4 出口和结果分别交付。具体拆分随依赖调整，但不把 L3/L4/结果默认合成一份巨大 PR。

## 4. 每个 PR 的交付材料

PR 描述必须让未参与对话的人也能审查：

1. 对应需求：文档章节、行为规则 ID 或问题编号；有争议的规则标记待定。
2. 功能前后变化：从一个具体玩家操作说明现在会发生什么。
3. 实现过程：入口 UI → API → 条件判断 → 状态/数据变化 → 评分或不计分的原因。
4. 阅读顺序：列关键文件及用途，说明核心分支，不要求审查者逐行猜测。
5. 数据与兼容：迁移、接口变化、旧存档/旧规则是否兼容、回滚限制；不涉及写“不涉及”。
6. 验证：实际执行的命令及结果、演示入口或启动步骤、关键路径、异常路径、截图/录像/追踪文件。未执行或受阻须明确写出。
7. 已知限制：哪些内容暂未做、哪些参数仍为草案，是否影响本 PR 合并或阶段 UAT。

PR 描述模板：

~~~markdown
## 问题与结果
对应需求：
玩家执行……后，现在会……。

## 后台处理
UI / API：
前置条件与状态迁移：
行为规则与计分：
数据保存与恢复：
关键文件阅读顺序：

## 验证
代码版本（commit SHA）：
执行的检查与结果：
手动操作步骤及预期：
失败/重试/拒绝路径：
截图、录像、服务端追踪：

## 兼容与限制
迁移及旧存档：
回滚方式或限制：
尚未验证/尚未完成：
~~~

模板填写在 PR 描述中，不需要另做重复报告。文档 PR 可以将运行检查标为不适用，并说明文档链接/一致性验证；生成文件或锁文件较大时单独解释，不以固定行数作为唯一质量门槛。

## 5. 代码审查重点与合并条件

George 优先核对：

- 业务：前置条件、动作顺序、拒绝/返回路径、L2 四组、是否存在死锁或越级推进。
- 评分：由后端判定；重复动作、复合事件和重试不重复计分；2:3:3:2 归一计算、16 型边界有依据。
- 存档：事件和检查点一致；草稿不提前计分；断线/关闭恢复不丢失已同步动作、不篡改历史结果。
- 接口与权限：只允许本人或明确授权测试人员访问；客户端不能自报分值或解锁；追踪接口由后端鉴权。
- 代码：职责清楚，变量命名对应业务，注释解释非显然规则；避免无关重构和不必要依赖。
- 验证：重要路径有可复现证据；预期值源于已确认需求或独立计算，不能只复制实现再验证自身。
- 兼容：新规则不改变老会话，迁移和资源更新不破坏旧存档。

合并条件：范围完整且无隐藏依赖；适用检查通过；阻塞意见解决；George 对当前版本明确认可；无尚未确认却被写死的关键业务规则。审查后有实质逻辑变更，标出新增差异并重新请求相关审查。

暂未配置分支保护时，这些是人工协作规则，不声称 GitHub 已强制执行。建议后续配置 MVP_branch 必须 PR、至少一名审查者、必要检查、禁止强推；需实际配置后才能记录为已启用。

## 6. UAT 必须展示真实后端过程

准备一个仅授权测试人员访问的只读“行为与评分追踪面板”，最好从首个可玩功能开始逐步实现。普通玩家不能访问，不能只靠隐藏按钮限制；API 需后端角色/权限校验。它是验收工具，不是可修改分数的运营后台。

| 面板项目 | 应展示的实际数据 |
| --- | --- |
| 环境与版本 | 测试 URL、构建 commit SHA、content/scoring/persona 版本、配置 hash |
| 会话与动作 | 测试 session_id、action_id、request_id、服务端时间与事件顺序 |
| 后端判定 | 接受/拒绝/重复请求、前置条件、规则 ID、互斥/覆盖原因 |
| 状态变化 | 动作前后 scene、revision、物品、门窗状态、任务进度 |
| 评分贡献 | 本次四轴增量、累计有效贡献、被忽略/替代项及原因 |
| 最终计算 | 原始分、槽分母与权重、关卡归一分、20/30/30/20 贡献、阈值和类型 |
| 保存与恢复 | 已同步检查点、草稿版本、待同步动作、恢复来源、冲突处理 |
| 有效计时 | 已确认活动区间、暂停原因、阈值判断，不把断网时间补算 |

数据必须来自实际后端处理记录与结果快照。面板不另算一套“正确答案”冒充真实执行；本地 outbox/未同步草稿明确标为客户端数据，不能伪装已落库。

建议后端支持按测试会话读取 trace 的只读接口；记录 accepted/rejected/duplicate 的尝试结果与持久事件的区别，重复请求不创建第二份评分事件。trace 查询应有分页/游标和最近更新标识，未更新不能误判为动作成功。

每个 UAT 会话可导出脱敏 JSON，包含版本、必要事件、规则引用与结果分解。禁止导出 Cookie、token、数据库密码或其他玩家数据。验收使用合成测试会话，日志保留期与数据删除策略同步确定。脱敏人工说明无法替代真实 trace。

面板尚未完成时，可以先用授权的后端 trace 导出、API 响应和数据库只读核对支持阶段演示，必须注明工具状态；最终 UAT 按上述完整展示要求执行。

### 6.1 固定的三层验收视图

用户已明确要求：每关单独测试，每个 action 的计分可见，每关有独立总分，最后由关卡分数加权结算。面板必须提供以下三层，不能只显示 L1–L4 打包后的总结果。

| 层级 | 展示与操作 |
| --- | --- |
| Action 明细 | 按关卡和事件顺序查看动作、规则、A/V/T/F 增量、计分前后累计、是否实际入账以及未计分原因 |
| 关卡小计 | L1/L2/L3/L4 各自展示原始累计、归一分、覆盖率、20/30/30/20 权重及加权贡献；进入中/已结算标识清楚 |
| 最终结算 | 四关分数与权重逐项展开，四轴合计、阈值与类型；可点回关卡，再点回具体 action |

“总分”仍为四轴分值，不能默认把 A/V/T/F 相加。计分包含加、减、0 和待判定；并非每次点击必定加正分。复合行为在判定条件满足时入账，显示参与动作和结算触发动作；重复请求新增贡献为 0，被替代项显示撤销与净变化。详细对账契约见 [评分设计](scoring-design.md)。

本关未结束可查看 provisional 累计；本关结束立即产生独立 finalized 快照，无需等 L4。未完成整局不得把缺失关卡当 0 或重分权重生成最终结果。最终结果引用四份关卡快照，并能复算每个维度的贡献。

### 6.2 每关用例必须包含逐步预期

每份关卡用例都包含：case_id、关卡/场景、前置存档或 fixture、代码与规则版本、操作序列、逐 action 的预期规则/分值、关卡预期原始总分/归一分、实际记录与结论。不能只写“玩完 L2 应出现结果”。

可从专用测试 fixture 建立关卡入口，方便 George 单独验收 L2/L3/L4；fixture 的物品、前置进度与来源必须标注。准备 fixture 仅限隔离测试环境/测试脚本，不给普通玩家开放跳关接口，也不绕过真实 action 校验。各关单测通过后仍需真实 L1→L4 全链验收。

逐 action 模板（每关一份，不预填通过）：

| 步骤/action | 前置状态 | 预期规则/计分状态 | 预期 ΔA/ΔV/ΔT/ΔF | 预期关卡累计 | 实际增量与累计 | 后端事件/证据 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 待填写 | 待填写 | 命中/无分/待判定/拒绝/重复 | 待按已确认规则填写 | 待独立计算 | 待执行 | 待补充 | Not run |

关卡结算模板：

| 关卡 | 有效贡献列表/快照 ID | 原始 A/V/T/F | 归一 A/V/T/F 与计算依据 | 权重 | 加权贡献 | 状态/结论 |
| --- | --- | --- | --- | --- | --- | --- |
| L1 | 待填写 | 待填写 | 待填写 | 20% | 待计算 | Not run |
| L2 | 待填写 | 待填写 | 待填写 | 30% | 待计算 | Not run |
| L3 | 待填写 | 待填写 | 待填写 | 30% | 待计算 | Not run |
| L4 | 待填写 | 待填写 | 待填写 | 20% | 待计算 | Not run |

新增必验项：逐 action 净变化与前后累计对账；本关有效贡献和关卡总分对账；关卡结算后独立可读；重复/断线恢复不重复入账；序列最终判定可反查前置 action；四关加权贡献和最终四轴分数对账。任何一层差异都作为缺陷记录，不能用最终类型恰好相同掩盖计算错误。

## 7. UAT 执行顺序

1. 开发方提交候选版本、需求映射、测试用例与已知限制；关键业务待定项先明确，否则对应项标记 Blocked。
2. George 部署/提供测试环境，核对实际运行 commit SHA、数据库迁移、内容和评分版本；明确是未合并 PR 预览还是已合并测试版本。
3. 为本轮建立独立测试会话与数据；按步骤操作，先记预期再记实测。
4. 同时观察 UI 和后台 trace；保留关键证据，不能只凭“看起来正常”通过。
5. 为每项记录 Pass、Fail、Blocked 或 Not run。自动化测试、模拟器和真机证据分别标注。
6. 失败项关联 issue/缺陷编号与修复 PR；修复后记录新 SHA，复测失败项及受影响路径。
7. George 记录技术/业务过程核对结论，项目负责人记录体验与业务规则结论；明确签认范围与未验收内容。
8. 最终候选版本完成四关串联回归和跨关存档恢复，再形成最终 UAT 结论。

通过某个功能的阶段 UAT 不等于整个产品已验收；修复后的版本也不自动继承所有旧版本的通过结论。最终交付要能追溯哪些证据适用于当前版本。

## 8. MVP 验收清单

| 用例 ID | 场景 | UI 与后台共同预期 |
| --- | --- | --- |
| UAT-SAVE-01 | 中途关闭/主动保存退出再进入 | 同场景恢复，已同步选择/物品不丢失 |
| UAT-SAVE-02 | 服务端处理成功但响应丢失，随后重开 | 原 action_id 补确认，事件/计分只生效一次 |
| UAT-SAVE-03 | 家具草稿离线保存后退出与恢复 | 布局恢复、同步来源明确、确认前不计分 |
| UAT-L1-01 | 四种过河方式分别尝试 | 合法通行、互斥路径正确，不能反复刷进度分 |
| UAT-L1-PADDLE | 船桨 1–5 次、重复第 5 次、存档后继续 | 前 4 次增量 0，第 5 次 (-1,-1,-1,+2) 一次；4 次后恢复仍需第 5 次；补发不加次数 |
| UAT-L1-02 | 人物/灯不同顺序及不点亮灯 | 所有符合条件的规则均累加并逐条可查，同一规则重复请求不重复入账 |
| UAT-L2-01 | 进入失联房间 | 每局四组均提供，不抽三组；拒绝后续路线待设计师决定，相关流程先记 Blocked |
| UAT-L2-02 | 首把钥匙失败、拒绝/再次尝试 | 已明确状态与计分可查；拒绝后的下一步等待设计，不虚报该路径通过 |
| UAT-L2-03 | 耳环 14999/15000/15001ms | 前两者返回时按短寻找，等值继续不计长寻找；持续至 15001ms 才触发长寻找；后台/旋屏/断网暂停可追溯 |
| UAT-L2-04 | 最终 Figma 家具交互及不同屏幕 | 有效 action 对应固定规则，预览/草稿不计分；不另加自由布局自动分类 |
| UAT-L3-01 | 门、等待、窗帘、窗与风扇不同选择 | 已明确 action 的状态和分值一致；不开/不关门的风暴流程待设计师决定 |
| UAT-L3-02 | 不带物品/九种物品/更改未确认选择 | 只带一件；“是”与具体物品分值累加，各计一次，预览切换不增分 |
| UAT-L4-01 | 四出口分别选择，结算时重试 | 一个最终出口，一个结果快照 |
| UAT-SCORE-01 | 独立已知行为轨迹 | 四轴按归一和 20/30/30/20 计算，类型映射一致 |
| UAT-SCORE-02 | 发布新规则后继续旧会话 | 旧版本不变；新会话使用新版本 |
| UAT-SCORE-03 | 每关逐 action 执行与单关结算 | 前后累计、有效贡献、关卡原始/归一总分逐层对账，未完成整局也可查单关 |
| UAT-SCORE-04 | 四关快照加权核对 | 逐关贡献可复算，最终四轴等于各关归一分按 20/30/30/20 加权之和 |
| UAT-UI-01 | 手机竖屏/横屏、桌面、触屏无 hover | 竖屏提示原文、横屏可操作、关键物件不遮挡 |
| UAT-ACCESS-01 | 普通玩家访问 trace 或他人存档 | 后端拒绝且不泄漏其他会话内容 |
| UAT-E2E-01 | 完整四关→结果→重玩 | 叙事连贯、每局独立、后台全链可追溯 |

上述为最小覆盖，具体步骤和预期数值应在各功能交付时补齐。未冻结的边界与剧情路径不能把工程建议当最终正确答案；家具以最终 Figma 的 action 映射为准。详细异常矩阵参见 [保存与恢复](save-and-resume.md)、[评分设计](scoring-design.md) 与 [开发计划](development-plan.md)。

## 9. UAT 记录模板与缺陷处理

~~~markdown
# UAT 记录：<本轮功能或候选版本>
日期 / 执行人：

commit SHA / 内容版本 / 评分版本 / 文案版本：

范围 / 前置条件 / 已知限制：

| 用例 ID | 操作步骤 | 预期 UI 与后台结果 | 实际结果 | 状态 | 证据/缺陷链接 |
| --- | --- | --- | --- | --- | --- |
| 待填写 | 待填写 | 独立于实现确定 | 待执行 | Not run | 待补充 |

阻塞项：
修复 PR / 新 SHA / 复测结论：
George 审查结论与范围：
项目负责人业务结论与范围：
未执行项及后续安排：
~~~

状态定义：Pass=实际执行且符合预期；Fail=实际不符；Blocked=缺条件/规则/环境；Not run=未执行。空表、演示录像和开发者自测不能代填 George 的验收签认。

缺陷分级：
- 阻塞：无法继续主流程、丢失已同步存档、重复/错误计分、越权访问或严重数据不一致；必须修复并复测。
- 重要：关键交互、移动端操作或恢复体验明显不符；默认修复后验收。
- 一般：不影响业务结果的文案/轻微视觉问题；可记录后续计划，由验收方明确接受。

发布/最终验收条件：关键功能和异常路径通过、无未解决阻塞缺陷、必要版本与证据齐备；重要缺陷若延期必须有负责人明确决定和跟踪项，不能由开发工具自行降级。UAT 完成后是否上线及部署时机由项目负责人和 George 安排。

## 10. 文档与证据放置

本规则放在仓库 docs，与架构、评分、存档设计共同维护；后续可在 docs/uat/ 保存不含敏感数据的用例与验收摘要，按日期和候选版本命名。大型录像、原始 trace 放受控附件/测试存储，在 PR 或 UAT 记录中提供链接，不把凭据或真实玩家数据提交 Git。

本轮仅编写规则与文档入口，未创建 PR、修改分支保护、实现测试面板、发送消息或执行 UAT。
